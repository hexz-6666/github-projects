## 0. 结论先行

**当前不能直接按“已确认契约”实现本次新需求，因为新需求与冻结契约存在直接范围冲突，而不是普通增量。**

## 2. 数据源、标签语义、许可与使用限制

### 2.1 三类来源必须分离

| 来源 | 实体 | 标签 | 许可/限制 | 本项目可用方式 |
|---|---|---|---|---|
| 本项目虚构数据 | 订单/客户/告警 | 无真实欺诈标签；规则分只是风险排序 | 自有虚构，`DEMO-*`、`example.invalid` | 默认可运行路径 |
| Olist | 巴西电商订单、订单项、支付、评价、客户、卖家、商品、地理 | **无直接欺诈标签**；取消/退款/差评/延迟都不是欺诈真值 | CC BY-NC-SA 4.0：非商业、署名、许可链接、修改说明、相同方式共享 | 仅独立订单数仓演示；不得用于有监督欺诈训练/评估 |
| IEEE-CIS | 在线交易 + identity | `isFraud` 二元标签（仅该数据集内） | 规则 B.7：非商业、接收者同意；禁止公开再分发原始/行级数据；商业需书面授权 | 仅独立训练与时间切分评测；不得给 Olist 补标 |

Handbook 仅作教学参考：代码 GPL-3.0、正文/图片 CC BY-SA 4.0；独立 PKL 无许可证，复制/再分发阻塞。

### 2.2 标签语义红线

1. **订单取消、退款、差评、延迟、支付失败不是欺诈真值**，不得生成 `is_fraud=1`，也不得作为监督学习标签。
2. 人工复核的 `CONFIRMED` 只是复核人判断，存在偏差与不一致，**不是客观真值**；若未来用作弱标签，必须单独命名（如 `review_outcome`）并注明不可当基准真值。
3. 规则分 `score` 是风险排序分，不是概率；`risk_level` 是分箱；`alert_status` 是处置状态。四者继续分离。
4. IEEE-CIS 的 `isFraud` 只在该数据集、该时间范围内有效；迁移到 Olist 属于跨域，不能声称有效。
5. 任何合成 `is_fraud` 必须标注“模拟标签”，不得写成真实欺诈标签。

## 3. 与本次需求的接口/字段冲突

### 3.1 范围冲突（最高优先级）

| 新需求 | 冻结契约现状 | 性质 |
|---|---|---|
| Vue 五个业务页面 | 仅有健康面板；架构写“后续查询与复核界面” | 范围扩展，需新接口与新页面 |
| 权限与审计 | 明确“没有登录权限系统”，`reviewerId` 是客户端不可信输入 | **直接冲突**，复核身份语义必须改 |
| 导入任务协调 | 无导入 API、无批次状态表 | 新增 |
| 训练/评分/模型版本 | 只有固定规则 `DEMO_RULE`；DDL 约束 `model_type='DEMO_RULE'` | **直接冲突**，约束会拒绝训练模型 |
| 时间切分与不平衡指标评测 | 架构明确“不含模型训练与评估” | 新增 |
| Olist 订单数仓 | DDL 只允许 `SYNTHETIC`、CNY、三种状态 | **直接冲突**，现有约束会拒绝 Olist 数据 |
| IEEE-CIS 标签评测 | 无独立评测域；禁止跨源拼接 | 新增，必须独立 schema/表 |

### 3.2 具体字段/约束冲突

| 编号 | 现有约束/字段 | 冲突点 | 影响 |
|---|---|---|---|
| F1 | `ck_ods_synthetic CHECK (source_system='SYNTHETIC')` | 无法写入 OLIST/IEEE_CIS | Olist 导入必然失败 |
| F2 | `ck_dwd_origin CHECK (data_origin='SYNTHETIC' AND source_system='SYNTHETIC')` | 同上 | DWD 无法承接外部源 |
| F3 | `ck_dwd_currency CHECK (currency='CNY')`、DWS 同样只允许 CNY | Olist 实际币种需按文件确认（通常 BRL） | 导入被拒绝或被迫篡改币种 |
| F4 | `ck_dwd_status CHECK (status IN ('CREATED','PAID','CANCELLED'))` | Olist 是履约状态（delivered/shipped/canceled/unavailable 等） | 语义被压扁，且易被误当欺诈状态 |
| F5 | `account_created_at NOT NULL`、`transaction_count_24h NOT NULL` | Olist 无账户创建时间；24h 频次需由历史订单推导 | 不能凭空造值；需可空/派生规则与新特征版本 |
| F6 | `ck_score_model CHECK (model_type='DEMO_RULE')` | 训练模型无法写入评分表 | 训练/评分链路被 DDL 阻断 |
| F7 | `ods_order_raw` 无数据集名、许可、源版本字段 | 外部数据血缘不足 | 无法证明来源与许可边界 |
| F8 | `ingest_batch_id` 只是字符串，无批次表 | 无法表达批次状态、失败、重试、幂等结果 | 导入协调无持久化依据 |
| F9 | `ads_alert_review.reviewer_id` 由请求体传入 | 可伪造身份；与“权限与审计”冲突 | 审计不可信 |
| F10 | 无用户/角色/审计事件表 | 权限与审计无落点 | 需新增表 |
| F11 | 无模型注册/版本/评测表 | 模型版本记录与指标无落点 | 需新增表 |
| F12 | IEEE-CIS 是 `TransactionID` 级交易，不是订单 | 强行塞进 `dwd_order` 会伪造订单语义 | 必须独立评测域 |
| F13 | Python `ScoreRequest` 固定 5 个特征 | 训练模型需要特征向量/版本 | 直接改会破坏 v1；应新增 v2 接口 |
| F14 | 错误码表无认证/CSRF/权限码 | 新接口错误语义未定义 | 需追加错误码，保持旧码不变 |

### 3.3 非冲突但需明确的契约点

- 金额契约继续有效：浏览器字符串、Java→Python JSON 数字、`DECIMAL(18,2)`。新增页面不得把金额改成 JS number。
- 健康语义继续有效：stub 不得冒充 MySQL；新增认证后健康端点仍应无敏感信息、可匿名探活。
- 评分不自动建告警的 v1 语义继续有效；自动告警应作为 v2 显式开关，不改变旧行为。
- `modelVersion`/`modelType` 必须可追踪；训练模型不得复用 `DEMO_RULE` 名称。

## 4. 标签泄漏、数据泄漏、域偏移与隐私风险

### 4.1 标签泄漏

| 风险 | 例子 | 处理 |
|---|---|---|
| 用结果字段做标签 | `order_status=CANCELLED`、退款、差评、延迟、客服结论 | 禁止作为 `is_fraud`；只能作为业务结果字段 |
| 用复核结论当真值 | `CONFIRMED` 直接当正样本训练 | 禁止默认这样做；如用，单列弱标签并评估偏差 |
| 用标签派生特征 | 退款金额、拒付结果、风控处置结果、事后冻结标记 | 训练特征必须按 `as_of` 截断，禁止事后字段 |
| 目标编码泄漏 | 全量数据算 target encoding | 只在训练折内拟合 |

### 4.2 时间与实体泄漏

- **禁止随机切分**。IEEE-CIS 按 `TransactionDT` 时间切分：早→训练、中→验证、晚→测试；报告每段正类率。
- 特征必须 as-of：`transaction_count_24h` 只能用当前时刻之前的窗口；Olist 的频次/客户历史同理。
- 同一实体不得跨训练/测试：按客户/卡/设备分组切分；IEEE identity 合并后按实体去重。
- 预处理（缺失填充、编码、缩放、阈值）只能在训练/验证上拟合；测试集只评估一次。
- 阈值选择用验证集；测试集报告固定阈值与固定 FPR 两种结果。

### 4.3 域偏移

- IEEE-CIS 是卡支付/在线交易欺诈；Olist 是市场订单履约。实体、特征、正类率、时间跨度、币种均不同。
- **不得**把 IEEE-CIS 训练模型说成“Olist 欺诈检测模型”，也不得在 Olist 上报告 IEEE 标签的指标。
- 若做演示迁移，只能称“跨域压力测试/不可比”，并单独报告，不得作为效果结论。
- Olist 没有欺诈标签，因此 Olist 侧只能做无监督异常、规则排序、数据质量与人工复核流程演示，不能报监督指标。

### 4.4 数据泄漏与隐私

- 禁止按金额、时间、序号、哈希把 Olist 与 IEEE-CIS 记录拼接或互贴标签。
- Olist 含评价文本、地理、`customer_unique_id` 等准标识；评价文本可能含个人信息，默认不导入、不展示。
- IEEE-CIS 含卡/地址/邮箱域/设备等敏感或准标识字段；只做本地非商业使用，不导出原始行、不提交训练产物、不公开模型（可能记忆数据）。
- 前端与 API 不返回原始载荷、完整邮箱、地址、卡标识；日志不记录请求体、标签、特征明细、凭据。
- 演示账号仅虚构；密码哈希存储；密钥只从仓库外注入；`.env` 不入库。

### 5.1 需要特别指出的“不是错误但会被误用”的点

- 固定规则文档写“未做精确率/召回率评估”，这是诚实声明；新需求要求评测时，**不能给规则分补一个伪造的 ROC-AUC**。规则分可以在 IEEE 上做“规则基线”评估，但必须标明是规则而非训练模型。
- 复核 `CONFIRMED` 在数据库中表示“复核结论”，新页面不得显示为“已确认欺诈”。建议 UI 文案统一为“复核结论：确认风险/排除/证据不足”，并在详情页固定展示“非欺诈真值”声明。
- `storageMode=stub` 的 503 是预期降级；新页面不要把 503 当网络错误，也不要在 stub 下显示“系统正常”。

### 6.2 建议分期（每期可运行、可验收）

1. **M0 契约 v2 批准**：确认本文件冲突项与决策，不改代码。
2. **M1 数据库与导入**：V3 迁移、来源/批次/质量/审计/模型/评测表；Olist/IEEE 适配器；幂等与失败恢复测试。

4. **M3 模型服务**：特征处理、训练（IEEE-only）、模型注册、时间切分评测、指标；v1 规则保留。
5. **M4 业务 API 与页面**：订单概览、异常队列、详情复核、数据质量、模型评估五页；错误/空态/权限态。
